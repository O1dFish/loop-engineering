# Terminology

This document is the single authoritative terminology dictionary for Loop Engineering. It defines only the official terms, their meanings, and prohibited ambiguous alternatives. Role names must be used exactly as listed; they do not create aliases or assign roles by themselves.

| Official term | Meaning | Prohibited ambiguous alternatives or usage |
| --- | --- | --- |
| project-roadmap | The explicitly assigned role responsible for the project goal, Stage definition, Task definition, acceptance, Result evaluation, and continuation or termination decisions. The name is product- and model-neutral. | Do not substitute a product-bound or model-bound role name, Project Controller, Project Manager, Coordinator, or Supervisor for this role name. |
| Launcher | The explicitly assigned role responsible for reading collaboration rules and Stage context, creating Executor, maintaining Stage lifecycle, and handling STOP. | Do not use this name for a role that evaluates Results, judges execution quality, or makes project decisions. |
| Executor | The explicitly assigned role responsible for bounded Task execution, validation, and generation of TASK_EXECUTION_RESULT. | Do not use this name for a role that defines successor Tasks or makes continuation or termination decisions. |
| Stage | A Loop lifecycle concept defined by project-roadmap and maintained by Launcher; its context is known to those roles. | Do not use Stage as another name for Task or as a collaboration message, protocol, or state machine. |
| Task | A bounded unit of execution whose identity, objective, scope, and acceptance are defined by project-roadmap. | Do not use Task as another name for Stage, an entire project, or an informal discussion. |
| Continue decision | The project-roadmap decision that another Task is required. When further execution is required, the decision is expressed by producing a new PROJECT_EXECUTION_REQUEST for the successor Task. | Do not treat a successor Task description or natural-language discussion as the execution request, or allow Launcher to infer one. |
| PROJECT_EXECUTION_REQUEST | The existing structured message generated by project-roadmap to express that a defined Task, including a successor Task after a Continue decision, is to be executed by Launcher. | Do not substitute a natural-language instruction or successor Task description for this message. |
| TASK_EXECUTION_RESULT | The existing structured message generated by Executor to report bounded Task execution and validation facts directly to project-roadmap. References to Result in the Contract refer to this message. | Do not use an informal report as a substitute for this message, or treat its completion status as project acceptance, Stage completion, or a continuation decision. |
| Notification Skill | An optional observability capability that may be used by Launcher or Executor. It is outside the Loop Contract and collaboration message set, owns no lifecycle control, and does not affect Task execution. | Do not treat notifications as collaboration messages, lifecycle control, or a prerequisite for Task execution, Result generation, or the Stage decision. |
| Loop | The lifecycle from project-roadmap initialization through Stage creation, Launcher initialization, Task execution, Result evaluation, and a continuation or STOP decision. | Do not use Loop to mean one Task execution or an automatic retry process. |
