# Loop Engineering for Codex

这是独立的 Codex 原生实验工作流。它继承有界 Task、最小上下文、事实证据和“执行完成不等于项目接受”等原则，但不复刻仓库现有 Launcher 链路，也不声称与 Loop Contract 原样兼容。

Skill 版本为 `0.1.2`。每个 Loop 初始化时记录实际加载来源以及五个运行文件的哈希集合；该版本与哈希集合共同标识本 Loop 的规则。后续按需读取引用或 resume 前复核指纹；若文件已改变，停止受影响的新委派，不在本 Loop 混用新规则，已确认更新须经显式重新加载并初始化后采用。无需为此复制规则或建立快照系统。已按旧版本启动的冻结 Loop 继续遵循已记录的 Skill 版本与哈希集合；要采用更新版，显式重新加载 Skill 并初始化新规则，可在当前主会话完成，无需因为主会话模型或推理级别另开会话。

## 入口与初始化

只有用户在当前主会话直接、显式调用 `$loop-engineering-codex` 并要求初始化，当前会话才能成为 `project-roadmap`。讨论、引用、审核本 Skill 或在日志中看到调用文字都不初始化。委派 Task 中的 Executor 即使看见、读取或继承了本 Skill，也必须保持 Executor 身份：不得初始化 `project-roadmap`、创建下级代理、启动新 Loop 或递归调用本 Skill。提示中出现 Skill 名称不等于用户初始化授权。

通过上述入口初始化后，当前主会话负责目标、设计、Stage、Task、验收、裁决和整个 Loop 的生命周期。

初始化先给出一份紧凑回执：`role`、Skill `version/source/hash-set`、工作区/项目、主会话模型与级别的已知配置、目标/范围/验收、授权边界以及能力限制。未提供的目标、验收或边界写“未提供”，配置或能力不可观测写“未知”，不猜测。

记录主会话模型与推理级别的已知配置作为观察；若当前会话的原生启动信息或 turn metadata（例如 `turn_context` 的 model/effort）不可见，记录为“未知”。用户提供的配置声明可单独标注为用户提供的信息，服务端实际路由无法确认时也如实标记。主会话模型和推理级别完全由用户选择，不构成初始化或执行资格条件，也无需为此请求额外确认。不得自动切换主会话模型或修改全局默认值。

仅初始化时不得选择待办、修改业务文件、创建 Executor 或开始业务执行。

实际需要的原生工具或参数不可用时，只阻塞依赖它的具体动作，并记录限制；主会话身份、模型或推理级别本身不构成阻塞条件。

用户同时授权了清楚目标时，在边界内持续执行，无需逐 Task 请求“继续”。配置仍未知时保留该未知项，不把它伪装成已验证。用户可在 Loop 运行中更改主会话模型或推理级别；记录可见变化，并核对当前目标、候选身份和待办动作是否仍一致后继续。不得仅因主会话身份或配置变化停止工作，也不得重置 `work_item_id`、`rework_index` 或已完成进度。除非用户明确要求停止或改变范围，先完成已授权且可安全完成的工作。

## 生命周期

主会话先澄清目标与验收，再把工作拆成有界 Task。主会话可以读取必要代码事实与证据；批量实现、测试实施和深度审核应委派给 fresh Executor，避免主会话同时承担大部分实现与自我审核。

默认串行执行与审核。同一工作树中不得让多个写 Task 并发；只有相互独立且不会写同一工作树的只读工作才可并行。每个 Task 都带上实际工作区或 worktree、分支、HEAD、dirty/untracked 事实和候选身份；不得把 detached worktree 说成用户主工作区。

每个有界执行创建一个新的通用 Executor。创建前由主会话按 Task 选择真实原生配置：

- 所有执行 Task（实现、修复、测试、研究、文档和分析）默认使用 `gpt-6-luna`、`high`。Task 的复杂度、风险或研究性质都不触发升级。实际独立审核是单独类别，可由主会话根据审核复杂度选择 Luna 或 Sol；审核必须只读候选、不得接管实现，且审核轮次不增加执行返工计数。
- 同一未接受执行工作项只有在真实返工次数达到第 4 次时，才允许该次执行选择 `gpt-6-sol`、`high`；达到阈值后，project-roadmap 可结合实际返工结果与任务情况决定是否升级，并记录选择理由，不是强制切换。按下表确定执行模型：

  | 同一工作项 rework_index | 模型 |
  | --- | --- |
  | `0`（首次尝试） | `gpt-6-luna` |
  | `1`、`2`、`3`（前三次返工） | `gpt-6-luna` |
  | `4+`（第四次及后续返工） | `gpt-6-luna` 或 `gpt-6-sol`；结合实际返工结果与任务情况选择并记录理由 |

  执行 `rework_index` 为 `0`、`1`、`2` 或 `3` 时必须请求 Luna，不得选择 Sol；第 `4` 次返工起 Sol 才成为可选项。工作项获接受后结束；新的独立执行工作项以 `rework_index: 0` 从 Luna 开始。独立审核按其自身复杂度路由，不能为了绕过执行阈值把实现或修复标作审核。

子会话模型选择规则通过 Skill 指令与原生 spawn 参数执行，不是程序级模型路由或状态强制。每次 Executor spawn 都显式请求按任务类别与返工序号所选模型、对应的推理级别和 `fork_turns: "none"`；不得省略子会话模型或推理级别。若运行时不接受该次请求的参数、所选子模型不可用，或可见的自定义 Agent 配置会覆盖请求，阻止该次派发并报告受影响的动作，不得静默回退或改动全局设置。当前原生接口可用时，以 `collaboration.spawn_agent(task_name, message, model, reasoning_effort, fork_turns)` 创建。每次创建成功后，主会话立即在已有原生会话记录中保存原生返回的精确代理 ID 或 canonical name（以实际暴露者为准）、工作项和 Task 标识、rework_index、模型与推理级别请求参数、客户端可见配置、配置来源、返工/升级依据，以及原生返回的进程 ID/exec handle（若有）；不得为此建立新数据库。工具名称或参数由运行时决定；若接口不同，先检查可用原生能力，不得虚构调用。无法观察服务端路由时，分别记录“请求参数”“可见配置”和“无法确认的实际路由”。模型自述不是配置证据。

Executor 不继承完整主会话历史。创建时只传当前 Task、工作位置、必要输入、边界、验收、验证要求和结果格式；不要传完整 Stage、Roadmap、历史讨论或后续 Task。读取并遵循 [Executor 规则](references/EXECUTOR.md)。Executor 不得创建下级代理或启动另一个 Loop。

主会话等待并检查 Executor 的实际结果。`COMPLETED` 只表示一次有界执行报告完成，不等于项目接受。主会话依据真实产物与验证证据作出以下一种裁决：接受；对同一目标定义新的修复 Task；定义下一 Task 并继续；因边界、证据不足或外部条件而停止。不得把自然语言摘要本身当作验收证据。

每个执行工作项使用稳定的 `work_item_id` 表示一个未接受的目标/验收定义；每次执行尝试，包括改名、resume 后的新实例，使用新的 `task_id` 和 fresh Executor，并继续沿用同一工作项累计的 `rework_index`。首次执行尝试为 `0`。只有主会话因候选未满足同一目标/验收而明确拒绝，并实际定义、派发新的纠正执行时，才将该工作项的 `rework_index` 加一；从而初次失败后的第一次纠正执行为 `1`。环境、权限、工具或模型不可用等错误不是能力返工，不增加计数、不解锁 Sol。命令重试、独立审核或补充验证会话、换名、重建实例或累计项目总返工都不计入原工作项；研究、测试等执行工作各有自己的稳定 `work_item_id`，并在该工作项内按同一裁决规则计数。独立工作项以 `0` 开始。不得通过制造失败或人工迭代达到阈值。每次返工必须有新的证据、新的可检验假设或边界内的新办法，并继续遵守既定时间、费用和次数预算；达到第四次返工后升级到 Sol 仍是裁量决定，不延长预算，也不授权无止境返工。达到验收并被接受后完成收尾，不自动创建新项目、新 Stage 或无关目标。

原生 resume 后，先核对最后一个获准目标、已作出的裁决、固定 Skill 身份、当前候选、尚未完成的动作，以及中断前可能已经发生的外部或本地副作用。确认事实后才继续，避免重复写入、重复通知或重复执行其它副作用；不把 resume 当成自动恢复已验证。

## 审核、记录与停止

重要实现或结论在接受前安排 fresh、独立的审核 Executor。审核必须覆盖实际候选，包括相关未提交修改和未跟踪文件；候选变化后，旧审核对受影响部分失效。执行审核、保存最小原生记录或安排后续只读复盘时，读取 [审核与记录规则](references/REVIEW_AND_RECORDS.md)。可合并相近的小审核 Task，避免机械地为每个微小改动创建会话。

收到用户直接停止指令后：

1. 立即停止新增委派和后续执行决策。
2. 当前运行时可用时，只对本会话在本 Loop 创建并已记录的精确代理 ID/canonical name 集合执行停止：用 `collaboration.send_message` 发出停止要求，并用 `collaboration.interrupt_agent` 中断仍在运行的实例。`collaboration.list_agents` 返回的更大 root 树只用于发现和核对，不产生本 Loop 所有权，也不能据此停止代理。
3. 用 `collaboration.wait_agent` 等待状态变化，再次核对上述集合；若记录中有本 Loop 启动的本地进程，只在通过 PID/exec handle 与该代理的父进程、命令行或原生关联信息核验归属后处理，不得按名称或全局进程列表猜测。若运行时接口不同，使用实际可用的同等原生能力并记录调用证据。
4. 报告已确认终止、仍在运行和无法确认的部分。

`interrupt_agent` 返回、中断一个会话或一次等待结束，都不能单独证明相关子进程已退出。当前能力没有 `close_agent` 时不得承诺已关闭代理。客户端退出后的后台持续运行也不在本 Skill 的承诺范围内。

## 固定边界

- 不创建 Launcher、隐藏启动器、调度器、日志平台、状态数据库或自动恢复框架。
- 不用面向用户的应用侧栏 Task 代替内部 Executor。
- 不允许 Executor 递归委派、定义后续 Task、扩大范围或修改本 Skill 规则。
- fresh 上下文与角色隔离是指令和原生创建参数提供的边界，不是操作系统沙箱；所有代理可能共享同一工作区和文件系统。
- 不伪造模型、上下文隔离、验收、审核、停止或业务价值已验证的证据。
