# Loop Engineering for Codex

这是独立的 Codex 原生实验工作流。它继承有界 Task、最小上下文、事实证据和“执行完成不等于项目接受”等原则，但不复刻仓库现有 Launcher 链路，也不声称与 Loop Contract 原样兼容。

Skill 版本为 `0.1.4`。每个 Loop 初始化时记录实际加载来源以及五个运行文件的哈希集合；该版本与哈希集合共同标识本 Loop 的规则。后续按需读取引用或 resume 前复核指纹；若文件已改变，停止受影响的新委派。冻结的 `0.1.3` Loop 继续遵循原来记录的版本、哈希集合和规则，旧返工选型仅适用于该冻结版本。只有用户显式重新加载 Skill 并初始化新的 `0.1.4` Loop 后，其新任务才采用本规则。可在当前主会话完成初始化，无需复制规则、建立快照系统或仅因主会话配置变化另开会话。

## 入口与初始化

只有用户在当前主会话直接、显式调用 `$loop-engineering-codex` 并要求初始化，当前会话才能成为独立 Loop 的 `project-roadmap`。讨论、引用、审核本 Skill 或在日志中看到调用文字都不初始化。在 PAC 或任何其他流程中获委派的 Executor 即使看见、读取或继承了本 Skill，也必须保持原有身份，不得初始化 `project-roadmap`、创建下级代理、启动新 Loop 或递归调用本 Skill。提示中出现 Skill 名称不等于用户初始化授权。

通过上述入口初始化后，当前主会话负责目标、设计、Stage、Task、验收、裁决和整个 Loop 的生命周期。

初始化先给出一份紧凑回执：`role`、Skill `version/source/hash-set`、工作区/项目、主会话模型与级别的已知配置、目标/范围/验收、授权边界以及能力限制。未提供的目标、验收或边界写“未提供”，配置或能力不可观测写“未知”，不猜测。

记录主会话模型与推理级别的已知配置作为观察；若当前会话的原生启动信息或 turn metadata（例如 `turn_context` 的 model/effort）不可见，记录为“未知”。用户提供的配置声明可单独标注为用户提供的信息，服务端实际路由无法确认时也如实标记。主会话模型和推理级别完全由用户选择，不构成初始化或执行资格条件，也无需为此请求额外确认。不得自动切换主会话模型或修改全局默认值。

仅初始化时不得选择待办、修改业务文件、创建 Executor 或开始业务执行。

实际需要的原生工具或参数不可用时，只阻塞依赖它的具体动作，并记录限制；主会话身份、模型或推理级别本身不构成阻塞条件。

用户同时授权了清楚目标时，在边界内持续执行，无需逐 Task 请求“继续”。配置仍未知时保留该未知项，不把它伪装成已验证。用户可在 Loop 运行中更改主会话模型或推理级别；记录可见变化，并核对当前目标、候选身份和待办动作是否仍一致后继续。不得仅因主会话身份或配置变化停止工作，也不得重置 `work_item_id`、`rework_index` 或已完成进度。除非用户明确要求停止或改变范围，先完成已授权且可安全完成的工作。

## 生命周期

主会话先澄清目标与验收，再把工作拆成有界 Task。主会话可以读取必要代码事实与证据；批量实现、测试实施和深度审核应委派给 fresh Executor，避免主会话同时承担大部分实现与自我审核。

默认串行执行与审核。同一工作树中不得让多个写 Task 并发；只有相互独立且不会写同一工作树的只读工作才可并行。每个 Task 都带上实际工作区或 worktree、分支、HEAD、dirty/untracked 事实和候选身份；不得把 detached worktree 说成用户主工作区。

### 按任务选型与原生派发

每次有界执行尝试创建新的通用 Executor。`project-roadmap` 按当前任务的范围、独立验收条件、复杂度和风险选择并记录理由。同一规则用于首次尝试和每次返工。

- 确定性的微小检查可由主会话直接运行，无需派发。例如读取当前分支与 HEAD。
- 对上下文紧凑、边界明确且可独立验证的集中或可重复任务，优先考虑 `gpt-6-luna`，如单模块修复及其针对性测试。初选 `high`。
- 对跨模块联动、需求或证据存在实质歧义、权限边界敏感或失误代价高的任务，可直接选择 `gpt-6.2-sol`，初选 `high`。例如核对跨仓库候选、权限边界与回滚条件。选型与 `rework_index` 解耦，无固定模型配额。审核按其自身的复杂度和风险选型。主会话可参考 `gpt-6.2-sol` 和 `high`，模型与推理级别仍由用户选择。

派发前核对目标 Codex 宿主、账号和 provider 的原生 `model/list`，确认所选模型及其 `supportedReasoningEfforts`。仅当当前任务适用并明确记录理由时，才可选择目录列出的其他推理级别。另核对当前可调用的原生 spawn 及其参数，确保它接受该模型、推理级别和 `fork_turns: "none"`。可用接口为 `collaboration.spawn_agent(task_name, message, model, reasoning_effort, fork_turns)` 时，每次显式传 `model`、`reasoning_effort` 和 `fork_turns: "none"`，包括独立审核。任务提示中的模型文字无法设置原生配置。

派发前核对使用的 Agent 及其有效配置。省略配置时可能使用 `[agents]` 默认值或继承主会话。自定义 Agent 文件中的 `model` 和 `model_reasoning_effort` 优先于对应的 spawn 值，须分别核对。目录或接口无法确认、模型或级别不受支持、请求被拒绝或有效配置会改写所选值时，报告具体受阻的派发及原因。不得静默降级、改动全局设置或用提示文字替代参数。

创建后立即核对能与精确代理 ID 或 canonical name 对应的原生会话或 turn metadata。记录工作项、Task、`rework_index`、选择与返工理由、请求的模型和级别、客户端可见配置及其来源，以及原生返回的进程 ID/exec handle（若有）。可见配置不符时报告差异，无法核对时标记未知。只有配置相符才报告所选配置可见；服务端实际路由与用量仅凭各自证据报告。模型自述和调用成功都不足以确认有效配置。沿用既有原生记录。

消息或 resume 只沿用既有会话的可见配置，除非该原生调用明确支持逐 turn 模型和推理级别覆盖，且回读证实生效。新执行尝试始终使用 fresh Executor。后续有界 Task 需要不同配置而当前接口无法逐 turn 覆盖时，在获准的安全边界新建适合的子会话，保留工作项与累计返工计数，不因配置变化中断在途工作。

Executor 不继承完整主会话历史。创建时只传当前 Task、工作位置、必要输入、边界、验收、验证要求和结果格式；不要传完整 Stage、Roadmap、历史讨论或后续 Task。读取并遵循 [Executor 规则](references/EXECUTOR.md)。Executor 不得创建下级代理或启动另一个 Loop。

主会话等待并检查 Executor 的实际结果。`COMPLETED` 只表示一次有界执行报告完成，不等于项目接受。主会话依据真实产物与验证证据作出以下一种裁决：接受；对同一目标定义新的修复 Task；定义下一 Task 并继续；因边界、证据不足或外部条件而停止。不得把自然语言摘要本身当作验收证据。

每个执行工作项使用稳定的 `work_item_id` 表示一个未接受的目标/验收定义。每次执行尝试，包括改名、resume 后的新实例，使用新的 `task_id` 和 fresh Executor，并继续沿用同一工作项累计的 `rework_index`。首次执行尝试为 `0`。只有主会话因候选未满足同一目标或验收而明确拒绝，并实际定义、派发新的纠正执行时，才将该工作项的 `rework_index` 加一。环境、权限、工具或模型不可用、命令重试、独立审核或补充验证、换名、重建实例及累计项目总返工均不增加原工作项计数。研究、测试等执行工作若有独立目标，从自己的稳定 `work_item_id` 和计数 `0` 开始。每次返工须有新证据、可检验的新假设或边界内的新办法，并遵守既定时间、费用和次数预算。模型选择不延长预算。工作项达到验收并获接受后完成收尾。

原生 resume 后，先核对最后一个获准目标、已作出的裁决、固定 Skill 身份、当前候选、尚未完成的动作，以及中断前可能已经发生的外部或本地副作用。确认事实后才继续，避免重复写入、重复通知或重复执行其它副作用；不把 resume 当成自动恢复已验证。

## 审核、记录与停止

重要实现或结论在接受前安排 fresh、独立的只读审核 Executor。审核须覆盖实际候选，包括相关未提交修改和未跟踪文件。候选变化后，旧审核对受影响部分失效。新候选发生实质变化时安排新的 fresh 审核，只能按 [审核与记录规则](references/REVIEW_AND_RECORDS.md) 复用原独立审核者执行精确的窄差异复核。可合并相近的小审核 Task。

收到用户直接停止指令后：

1. 立即停止新增委派和后续执行决策。
2. 当前运行时可用时，只对本会话在本 Loop 创建并已记录的精确代理 ID/canonical name 集合执行停止：用 `collaboration.send_message` 发出停止要求，并用 `collaboration.interrupt_agent` 中断仍在运行的实例。`collaboration.list_agents` 返回的更大 root 树只用于发现和核对，不产生本 Loop 所有权，也不能据此停止代理。
3. 用 `collaboration.wait_agent` 等待状态变化，再次核对上述集合；若记录中有本 Loop 启动的本地进程，只在通过 PID/exec handle 与该代理的父进程、命令行或原生关联信息核验归属后处理，不得按名称或全局进程列表猜测。若运行时接口不同，使用实际可用的同等原生能力并记录调用证据。
4. 报告已确认终止、仍在运行和无法确认的部分。

`interrupt_agent` 返回、中断一个会话或一次等待结束，都不能单独证明相关子进程已退出。当前能力没有 `close_agent` 时不得承诺已关闭代理。客户端退出后的后台持续运行也不在本 Skill 的承诺范围内。

## 固定边界

- 不创建 Launcher、隐藏启动器、调度器、日志平台、状态数据库或自动恢复框架。
- 不用面向用户的应用侧栏 Task 代替内部 Executor。
- 不允许 Executor 递归委派、定义后续 Task、扩大范围或修改本 Skill 规则。
- fresh 上下文与角色隔离是指令和原生创建参数提供的边界，不是操作系统沙箱；所有代理可能共享同一工作区和文件系统。
- 不伪造模型、上下文隔离、验收、审核、停止或业务价值已验证的证据。
